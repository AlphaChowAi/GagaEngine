# GagaEngine 设计文档

状态：草案 v0.1（讨论基线，尚未开始实现）

本文记录到目前为止达成的设计共识、尚未决定的问题，以及分阶段的实现路线。
标注为「已定」的条目是讨论中明确做出的决定；标注为「待定」的条目需要继续讨论。

---

## 1. 定位

GagaEngine 是一个**特用**游戏引擎，不是通用引擎。它只做一件事：

> 让游戏世界由「物质」构成，物理和化学行为由引擎根据物质属性推导，而不是由脚本逐个编写。

四个支柱：

1. **物理和化学原生**：资产描述的是「空间里哪里有什么物质」。质量、惯性、碰撞、导热、
   可燃性、反应性全部由引擎推导。
2. **描述式场景**：场景只声明物质、形状、初始状态和约束，不写「怎么动、怎么反应」。
3. **科学的描述系统和玩法系统**：描述语言和玩法规则本身懂量纲、物质和反应，
   不是把科学概念降级为浮点数和字符串标签。
4. **AI 原生**：大语言模型能读懂并写出场景、物质和玩法规则；引擎负责校验其正确性。

### 非目标

- 不做通用引擎（不追求覆盖任意类型的游戏）。
- 不做工程级仿真（数值不要求与现实吻合到可用于设计或科研）。
- 不做分子级或量子级模拟。
- 第一阶段不做游戏运行时的大模型角色（NPC、导演），只预留接口。

## 2. 设计原则

### 2.1 近似，但正确（已定）

这是贯穿全引擎的原则，明确划分「绝不能错」和「可以简化」。

**严格保证（守恒律与方向）：**

| 性质 | 含义 |
|---|---|
| 质量守恒，精确到元素 | 每条反应必须配平，加载时校验，不配平即拒绝 |
| 能量守恒 | 反应热由生成焓计算（盖斯定律），不手工填写 |
| 动量守恒 | 所有相互作用成对出现 |
| 热力学方向 | 热只从高温流向低温；反应能否自发进行由自由能决定 |
| 相变 | 吸放潜热；气体遵守状态方程 |

**允许近似（速率与精度）：**

- 反应速率按游戏时间标定，不照搬真实动力学。
- 用总包反应代替基元反应链。
- 空间分辨率有限，物质种类有限。
- 本构模型简化（粘度、弹塑性等）。

**可测试性**：每个模拟步之后可自动检查总质量、各元素总量、总能量、总动量。
「正确」是由测试断言的，不靠肉眼判断。

### 2.2 一个科学内核，多个系统共用（已定）

```
            ┌─────────── 科学内核 ───────────┐
            │ 量纲与单位 · 元素周期表 · 物质库 │
            │ 热力学数据 · 守恒律 · 反应规则   │
            └──┬────────────┬────────────┬──┘
          场景描述系统     模拟系统      玩法系统
```

「温度」「摩尔」「铁」在任何一层都是同一个概念。内核是唯一的事实来源。

### 2.3 只有一小部分世界是「活」的

性能策略的核心。静止、均匀的物体用便宜的表示；只有正在受热、流动、断裂、
反应的区域才升级为昂贵的场表示，事后再降级。

### 2.4 维度无关（已定：先 2D，后 3D）

- 2D 视为**单位厚度的薄片**：密度仍是 kg/m³，能量仍是焦耳，物质库升 3D 时不变。
- 不使用 2D 专属技巧（例如落沙式元胞自动机），采用对维度通用的连续介质方法。
- 代码对维度泛型（Rust 泛型 / Slang 泛型）。
- 2D 视角暂按**横截面侧视**（有重力）设计。【待确认】

## 3. 技术栈

| 项 | 选择 | 状态 |
|---|---|---|
| 宿主语言 | Rust | 已定 |
| 着色语言 | Slang | 已定 |
| 图形 API | Vulkan（直接使用，需要完整 bindless） | 已定 |
| 场景描述 | 自研 DSL | 已定（语法待定） |
| 数据组织 | 物体级 archetype ECS + 物质级稀疏分块网格（SoA） | 已定方向 |

选择 Slang 的理由：多后端输出、泛型与接口适合表达材料系统、自动微分对物理求解有用、
可编译到 CPU 作为对照。选择直接使用 Vulkan 的理由：需要完整的 bindless 和底层控制，
且不要求运行在浏览器中。

## 5. 科学内核

纯 CPU、无图形依赖的库，是其他所有部分的基础。

### 5.1 量纲与单位

- 所有物理量携带量纲（长度、质量、时间、温度、物质的量、电流、发光强度）。
- 内部统一使用 SI；输入可用常见单位（cm、°C、atm、mol/L 等）并自动换算。
- 量纲不匹配是编译错误。

### 5.2 元素与物质

- 元素表：符号、原子量等。
- 物质：化学式、相态相关属性（密度、比热、导热系数）、熔点、沸点、潜热、
  标准生成焓、标准熵，以及力学属性（弹性模量、屈服强度等）。
- 混合物：合金、溶液、气体混合物，以各组分的量来表示。
- **数据必须可追溯来源**。AI 可以提议新增物质，但须通过一致性检查，
  不允许未经核对的热力学数据进入物质库。

### 5.3 反应

- 一条反应只需声明：反应物、产物、动力学参数（如活化能、速率标度）。
- 内核自动完成：配平校验、反应焓计算、自发性判断。
- 速率采用 Arrhenius 形式，按游戏时间标定。

### 5.4 守恒检查

提供对任意世界状态计算总质量、各元素总量、总能量、总动量的函数，供测试和调试使用。

## 6. 场景描述系统（DSL）

语言本身懂科学。以下语法**仅为示意**，具体语法待定。

### 6.1 语言特性

```
// 物理量是带量纲的类型
width = 5 cm
temp  = 300 K
x = 5 kg + 3 m                      // 错误：量纲不匹配

// 化学式是字面量，反应是可校验的声明
water = H2O
steel = alloy(Fe: 98%, C: 2%)
brine = solution(NaCl in H2O, 3 mol/L)
reaction combustion: CH4 + 2 O2 -> CO2 + 2 H2O

// 用几何 + 物质 + 状态描述物体
tank = sealed vessel(steel, wall: 5 mm) {
    contains CH4 at 2 atm, 20 °C
}

// 用物理关系描述约束
beam welded_to wall
cup resting_on table
room in thermal_equilibrium at 293 K
```

### 6.2 几何

采用有符号距离场（SDF）的构造式几何：基本形状加布尔运算和变换。
理由：布尔运算代价低，天然支持碰撞查询、离散化到网格、破坏与熔化，且对维度通用。

### 6.3 分层校验

越早拦截越好，每层都输出结构化诊断：

| 层 | 检查内容 |
|---|---|
| 语法与量纲 | 语法错误、量纲不匹配、单位不存在 |
| 化学 | 反应配平、物质是否存在、热力学是否允许 |
| 场景物理 | 初始即破裂、无支撑物体、初始即发生剧烈反应等 |

诊断示例：

```
warning: 钠块在 t=0 与水接触，将立即剧烈反应
warning: 该梁无支撑，会在重力下坠落
error:   容器内压力超过壁面屈服强度，场景初始即破裂
```

## 7. 模拟系统

### 7.1 两层数据表示

- **物体级（ECS）**：每个物体是一个实体，带刚体状态和均匀的物质状态。便宜。
- **物质级（稀疏分块网格）**：每个单元存各物种的量、温度、速度等，SoA 布局，
  只为活跃区域分配。不为每个单元创建实体。

### 7.2 模拟分级

物体在两种表示之间按需升降级，转换时必须保持质量和能量守恒。
升降级的触发条件和策略是性能成败的关键，需要原型验证。【待定】

### 7.3 物理过程

- 刚体动力学与碰撞
- 导热
- 物质扩散与对流
- 相变
- 流体与气体
- 形变与断裂

### 7.4 化学过程

连续介质级：每个单元根据自身的成分和温度计算反应进度，反应热反馈回温度场，
进而影响物理（热膨胀、气体压力等）。

### 7.5 求解器选型【待定】

核心技术决策：固体、液体、气体使用统一方法（例如物质点法），还是各自使用专门方法再耦合。
需专门讨论并通过原型比较。

### 7.6 实现顺序

先写 **CPU 参考实现**，作为正确性的基准；再移植到 GPU（Slang 计算着色器）。
GPU 版本的结果必须能与 CPU 参考实现对照。

### 7.7 已知的硬问题

1. **时间尺度跨度大**：爆炸是微秒级，生锈是天级，需要按游戏时间重新标定。
2. **分辨率限制**：单元尺寸以下的现象（薄膜、界面混合）只能近似。
3. **内容规模**：必须限定为精选的物质集和反应集，全部数据驱动。
4. **刚性反应的数值稳定性**。

## 8. 玩法系统

玩法概念就是物理概念。

| 传统引擎 | GagaEngine |
|---|---|
| 伤害值、血量 | 由身体的温度、完整度、化学损伤推导【彻底程度待定】 |
| 武器有攻击力 | 工具是物理装置：打火机是热流，锤子传递动量 |
| 合成配方表 | 没有配方：冶炼是还原反应，合金是混合 |
| 触发器检测碰撞体 | 条件是带单位和时间的物理量谓词 |
| 资源是计数器 | 资源是物质和能量，全程守恒 |

### 8.1 与物质世界的交互方式

- **查询**：某区域的温度、浓度、连通性等。
- **事件**：点燃、断裂、相变、反应发生。
- **声明式规则**：

```
goal: beaker.pH in 6.5..7.5, held for 5 s
when furnace.temp > melting_point(Fe) -> emit "iron_molten"
fail: player.core_temp > 42 °C
```

### 8.2 原生积木

- 传感器：温度计、压力表、pH 计、秤等。
- 执行器：阀门、加热器、电机等。

### 8.3 设计者护栏

- 不可破坏的材料与可锁定的区域。
- 确定性模拟（固定种子），支持解谜验证与回放。

## 9. AI 原生

第一阶段的重点是 **AI 创作**：大语言模型编写场景、物质和玩法规则。（已定）

### 9.1 创作闭环

```
自然语言需求 → AI 写 DSL → 内核校验 → 结构化诊断 → AI 修正 → 通过
```

AI 负责创作，内核负责保证正确，不要求 AI 本身可靠。

### 9.2 对设计的要求

1. **沿用科学界已有的记法**（化学式、SI 单位、反应方程式），不自创符号。
2. **语法规则、声明式、语句可独立理解**，使用名字而非编号和魔法数字。
3. **语言规范足够短**，一份文档加一组示例即可让模型学会。
4. **诊断是给 AI 读的**：结构化、定位到语句、带修正建议。
5. **提供无界面的「编译并返回诊断」入口**，这是闭环的最小必要条件。

### 9.3 后续（预留，不在第一阶段）

- AI 操作引擎：运行、查询、回滚、试玩、验证谜题可解。
- 语义化的世界状态读出与因果链追溯。
- 游戏运行时由大模型驱动的角色：只能通过语义查询感知、通过物理执行器行动，且必须异步。

## 10. 路线图

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1 科学内核** | 量纲与单位、元素表、物质与热力学数据、反应配平与焓计算 | 单元测试覆盖守恒与量纲；已知反应的焓与文献值吻合 |
| **M2 描述语言** | 语法、编译器、三层校验、结构化诊断、语言规范文档 | 模型仅凭规范能写出通过校验的场景，并能依据诊断自行修正 |
| **M3 2D 模拟（CPU 参考）** | 稀疏网格、导热、扩散、反应、相变 | 每步自动通过质量、元素、能量守恒检查 |
| **M4 GPU 与渲染** | Slang + Vulkan，将 M3 移植到 GPU | 目标场景达到 60 fps，结果与 CPU 参考一致 |
| **M5 玩法系统** | 物理量谓词、传感器与执行器、目标与事件 | 一个可玩的小关卡 |
| **之后** | 升级到 3D | 物质库与 DSL 无需修改 |

M1 和 M2 是纯 CPU 逻辑，不依赖图形，最先完成，也最能体现引擎的独特性。

### 建议的代码组织（Cargo workspace）

```
crates/
  gaga-kernel/    科学内核：量纲、元素、物质、反应、守恒检查
  gaga-lang/      DSL：词法、语法、校验、诊断
  gaga-sim/       模拟：物质场、求解器（先 CPU）
  gaga-ecs/       物体级 ECS
  gaga-render/    Slang + Vulkan
  gaga-play/      玩法系统
  gaga-cli/       命令行：编译并输出诊断
data/             物质库与反应库
docs/             设计文档与语言规范
```

## 11. 待定问题

1. **求解器选型**：统一方法还是多方法耦合（第 7.5 节）。
2. **DSL 具体语法**：本文示例仅为示意。
3. **模拟分级策略**：升降级的触发条件与守恒转换（第 7.2 节）。
4. **角色是否完全物质化**：是否彻底取消血量等抽象数值。
5. **2D 视角**：侧视（当前假设）还是俯视。
6. **牵引游戏**：是否有一个具体的游戏类型来驱动需求和取舍。
7. **规模目标**：场景尺寸、单元分辨率、同屏活跃单元数、物质与反应的数量。
8. **物质库的数据来源与许可**。
