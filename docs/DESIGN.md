# GagaEngine 设计文档

状态：草案 v0.3（讨论基线，尚未开始实现）

v0.2 相对 v0.1 的主要变化：目标改为 3D；模拟以物体级为主，不再以逐格模拟为主；
魔法是世界规律的原生部分，取消「真实与虚构」的区分；加入场、时间与空间能力；
先做单人、之后加局域网联机；路线图改为先打穿一条最薄的可玩路径。

配套文档：[世界法则](WORLD_LAWS.md) 记录这个游戏世界的自然规律，是本引擎内核的输入数据。
本文只讲引擎如何实现，不重复法则的内容。

标注「已定」的是讨论中明确做出的决定；「待定」的需要继续讨论。

---

## 1. 定位

GagaEngine 是一个**只为我们自己的游戏负责**的引擎，不是通用引擎。（已定）

> 游戏世界按一套自洽的自然规律运转。物体的行为由引擎根据这套规律推导，而不是由脚本逐个编写。

| 项 | 决定 |
|---|---|
| 游戏类型 | 3D 动作冒险 |
| 人数 | 先做单人；之后加局域网联机；不做同屏分屏 |
| 引擎 | 自研，不背通用引擎的包袱 |
| 规律内核 | 独立的核心库，不依赖渲染和引擎其他部分 |

四个支柱：

1. **规律原生**：物体由物质构成，其物理、化学和魔法行为由引擎推导。
2. **描述式**：场景只声明有什么、处于什么状态，不写怎么动、怎么反应。
3. **描述系统和玩法系统懂规律**：量纲、物质、反应、场在语言层面就是一等概念。
4. **AI 原生**：大语言模型能读懂并写出世界定义、场景和玩法规则，引擎负责校验。

### 非目标

- 不做通用引擎，不追求覆盖其他类型的游戏。
- 不追求与现实数值吻合。现实是灵感和数据的来源，不是约束。
- 第一阶段不做游戏运行时由大模型驱动的角色，只预留接口。

## 2. 设计原则

### 2.1 自洽，而不是写实（已定）

「正确」指在世界法则之下**自洽、守恒、方向一致**。

- **严格保证**：能的总量、动量、电荷守恒；能顺势而流；转化的方向由能量差决定。
- **允许近似**：快慢、强弱、空间精度、物质种类的数量。
- **可测试**：每一步模拟之后可以自动核对总账。正确性由测试断言，不靠肉眼判断。

### 2.2 引擎代码里不出现世界的内容（已定）

内核实现的是一套**通用的规律框架**。「火」「灵能」「铁」这些词只出现在世界定义的数据里。
魔法因此不是特例：它和热、电一样，只是填进框架的规则。

### 2.3 一个内核，多个系统共用（已定）

描述语言、模拟、玩法使用同一套概念和同一份数据。内核是唯一的事实来源。

### 2.4 能不算的就不算（已定）

正确不等于精确。默认在**物体级**模拟：一个物体一组状态。能直接得出结果的不走过程。
只有确实需要空间分布的现象（烟、液体、火焰）才使用更细的表示。

### 2.5 求解器选成熟、保守的做法

这个引擎的独特之处是规律内核、描述语言和 AI 创作，不是求解器。求解器不冒险。

### 2.6 只深入基本规律，其余从简（已定）

投入只放在基本规律上：内核、模拟、描述语言。与规律无关的部分一律用最简单的形式，
够用即可：角色是一个胶囊体，物体是基本几何体，画面是最基础的着色，界面是调试文字，
不做动画、音频和关卡工具。等基本规律站稳之后，再按游戏的需要逐项补上。

### 2.7 由游戏牵引

引擎不脱离游戏单独推进。先做出一条最薄但可玩的路径，再逐层加深（见第 12 节）。

## 5. 规律内核

纯 CPU、不依赖图形的独立库。它不知道任何具体的元素或物质，只提供以下通用构件。

| 构件 | 含义 | 世界法则中的对应 |
|---|---|---|
| **量与单位** | 带量纲的物理量，量纲不符即报错 | 全文 |
| **物质** | 组成、归属的形、灵价、各项属性 | 第 3、4、8 节 |
| **领域** | 一种守恒的量被一种势推动，在物质中储存和流动 | 火、雷电、灵 |
| **过程** | 相变、反应、转换、凝与散 | 第 4 节 |
| **场** | 由源产生、作用于受体、随距离减弱 | 第 6 节 |
| **界的参数** | 时率、引力、空间连接 | 第 9 节 |

### 5.1 内核提供的推导

- 由灵价计算每条反应放出或吸收的能，并判断其方向。
- 由物质属性计算接触物体之间各领域的流量。
- 由源计算场对每个物体的作用，保证力成对出现。
- 生成元素关系图。

### 5.2 内核提供的校验

- 量纲一致；反应配平。
- **能量一致性**：任意两条到达同一结果的路径，能量差必须相等。
- **连通性**：每种元素都登记了与灵之间的转化，大循环成立。
- **总账核对**：对任意世界状态计算能、动量、电荷的总量，供测试使用。

## 6. 描述语言

一门语言，三种用途。具体语法待定。

| 用途 | 写什么 |
|---|---|
| **世界定义** | 领域、元素、物质及其属性、过程、场。即世界法则的可执行版本 |
| **场景描述** | 这里有什么物体，由什么构成，处于什么状态，彼此是什么关系 |
| **玩法规则** | 以物理量表达的条件、目标和事件 |

### 6.1 语言特性

- 物理量带单位；化学式和反应式是字面量。
- 沿用科学界已有的记法，不自创符号。
- 声明式，每条语句可以独立理解，使用名字而非编号。
- 规范足够短，一份文档加一组示例即可让模型学会。

### 6.2 分层校验

| 层 | 检查内容 | 方式 |
|---|---|---|
| 语法与量纲 | 语法、量纲、单位 | 静态 |
| 规律 | 配平、能量一致性、连通性、引用的物质是否存在 | 静态 |
| 场景 | 明显的问题，如物体重叠、缺少必填状态 | 静态 |
| 试运行 | 场景开始后实际会发生什么 | 无界面地短暂运行模拟 |

前三层是**读**出来的：只看写下的内容就能判断，瞬间完成，结论确定。
第四层是**跑**出来的：一个场景会不会自己烧起来、塌下来，取决于一连串相互影响的过程，
无法靠阅读预知，只能实际运行一小段时间，把期间发生的事件列出来。例如：

```
试运行 5 秒：
  0.2 秒  灵素块与水接触，开始剧烈反应
  1.5 秒  横梁失去支撑，坠落
  3.0 秒  之后无新事件
```

作者（人或模型）对照这份清单，判断这是不是自己想要的开场。

诊断是结构化的，定位到语句并带修正建议，供模型阅读。

## 7. 模拟系统

### 7.1 物体级为主

每个物体是 ECS 中的一个实体，带有一组状态：

- 组成（各物质的量）与形态
- 热含量（由它得出温度和相态）
- 电荷、灵能
- 位置、速度等刚体状态
- 时率

物体之间通过**接触**和**场**相互作用：

- 接触的物体之间，热、电、灵、物质按属性和势差流动。
- 反应发生在物体内部或接触处，消耗和生成的量不得超过现有的量。
- 场由源直接算出对每个物体的作用。

存热含量而不是温度：相变和潜热因此自然出现，不需要专门处理。

### 7.2 需要空间分布的现象【待定】

液体、气体、烟和火焰不能只用一组状态表示。方案待定，倾向于粗网格上的通量形式
（流出一格的必然流入相邻一格，守恒由结构保证），只在有活动的区域分配。

### 7.3 刚体与破坏

刚体动力学与碰撞采用成熟方案。物体被烧掉、腐蚀或击碎时，拆分为新的物体，
各部分的量之和等于原来的量。

### 7.4 时间与空间能力对模拟的要求

这些必须在设计之初就纳入，后加的代价很高。

| 要求 | 原因 |
|---|---|
| 每个物体有自己的时率 | 减速、加速、静止 |
| 确定性的模拟，以及完整的快照与恢复 | 整体回溯；同时是联机同步的基础 |
| 传送门 | 物理上要处理跨门的接触、流动和场 |
| 多个世界并存 | 储物空间是独立的小世界 |
| 引力是局部的 | 引力可以被改变，也可以由堆积产生 |

### 7.5 实现顺序

先在 CPU 上实现，作为正确性的基准。只有在确认性能不足的地方才迁移到 GPU，
迁移后的结果必须能与 CPU 版本对照。

## 8. 玩法系统

玩法概念就是规律中的概念。

| 传统做法 | 本引擎 |
|---|---|
| 伤害值、血量 | 由身体的状态推导【彻底到什么程度待定】 |
| 法术是独立的技能 | 没有法术，只有让灵能流过相晶 |
| 合成配方表 | 没有配方，制作就是转化 |
| 触发器检测碰撞体 | 条件是带单位的物理量谓词 |
| 资源是计数器 | 资源是物质和能，全程守恒 |

玩法层与世界的交互方式：

- **查询**：某物体或区域的温度、成分、灵能、连通性等。
- **事件**：点燃、凝固、断裂、反应发生等。
- **声明式规则**：以物理量写成的条件和目标。

留给设计者的护栏：不可破坏的物质、可锁定的区域、确定性的模拟。

## 9. AI 原生

第一阶段的重点是 **AI 创作**：大语言模型编写世界定义、场景和玩法规则。（已定）

```
自然语言需求 → 模型写描述语言 → 内核校验 → 结构化诊断 → 模型修正 → 通过
```

模型负责创作，内核负责保证自洽，不要求模型本身可靠。
模型已有的科学知识可以直接用于借自现实的部分；这个世界独有的部分由世界法则告知。

为此需要一个无界面的入口：编译、校验，并返回诊断。

后续预留：模型操作引擎（运行、查询、试玩）；游戏运行时由模型驱动的角色。

## 10. 渲染

Slang + Vulkan，自研。由游戏的需要决定做什么，目前已知的特殊要求：

- **传送门**：透过门看到另一侧。
- **形态变化**：物体会熔化、燃烧、冻结、碎裂，外观须随状态改变。
- **状态可读**：温度、带电、灵能等状态要让玩家看得出来。

原型阶段使用最简单的渲染，不提前投入。

## 11. 联机【待定】

先做单人。之后加入局域网联机。确定性的模拟使「只同步输入」成为可能，
但不同机器上保证完全一致的计算结果有难度，具体方案待定。

## 12. 路线图

原则：先打穿一条最薄的可玩路径，再逐层加深。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M0 最薄的一条线** | 内核只含少量物质和几种过程；最小的世界定义；物体级模拟（CPU）；最简单的 3D 画面；一个可以摆弄的小场景（例如木、水、冰、火，加一种相晶） | 能跑、总账守恒，并回答一个问题：摆弄起来有没有意思 |
| **M1 内核完整** | 全部通用构件；能量一致性与连通性校验 | 世界法则可以完整写成数据并通过校验 |
| **M2 描述语言与 AI 创作** | 语法、编译、分层校验、结构化诊断、语言规范 | 模型仅凭规范能写出通过校验的内容，并能依据诊断自行修正 |
| **M3 八元素与场** | 全部元素、相晶、四种场；需要空间分布的现象 | 世界法则中的组合举例都能自然发生 |
| **M4 时间与空间** | 时率、回溯、传送门、储物空间、引力改变 | 世界法则第 9 节的能力全部可用 |
| **M5 玩法系统** | 条件、目标、事件、护栏 | 一个完整的可玩关卡 |
| **M6 联机** | 局域网 | 两台机器结果一致 |

**M0 是止损点。** 如果摆弄起来没有意思，在这里调整方向，代价最小。

### 建议的代码组织（Cargo workspace）

```
crates/
  gaga-kernel/    规律内核（独立库）
  gaga-lang/      描述语言：语法、校验、诊断
  gaga-sim/       模拟
  gaga-render/    渲染（Slang + Vulkan）
  gaga-play/      玩法系统
  gaga-cli/       命令行：编译、校验、无界面运行
world/            世界定义（世界法则的数据版本）
docs/             设计文档、世界法则、语言规范
```

## 13. 风险

| 风险 | 说明 |
|---|---|
| **好不好玩** | 最大的风险，不是技术问题。由 M0 尽早检验 |
| **通用功能的工作量** | 角色控制、动画、镜头、关卡工具、音频、界面。按第 2.6 节，现阶段全部从简，推迟到基本规律站稳之后；但成品游戏最终离不开它们 |
| **传送门** | 同时影响渲染和物理的基础结构 |
| **液体与气体** | 物体级模拟覆盖不了，方案待定 |
| **跨机器的确定性** | 联机和回溯都依赖它 |
| **涌现带来的失控** | 玩家可能破坏关卡设计，需要护栏 |

## 14. 待定问题

1. 描述语言的具体语法。
2. 液体、气体、火焰的表示方式（第 7.2 节）。
3. 刚体与碰撞是自研还是采用现成的库。
4. 角色是否完全由身体状态推导，取消血量等抽象数值。
5. 联机的同步方案（第 11 节）。
6. M0 小场景的具体内容。
7. 世界法则中仍待讨论的问题，见该文档末尾。
